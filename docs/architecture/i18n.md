# Interface languages (i18n)

The web interface works in several languages. **The default is English**; the user changes it from the
language menu in the top bar (left of Product Tour, `EN`/`TR`). The choice is stored in the browser and in
the user's profile (`users.prefs.language`), so it carries over to other devices.

Library: **i18next** + **react-i18next**. Code: `apps/web/src/i18n/`.

---

## 1. Adding a new language (no code changes)

1. Create the folder:
   ```bash
   npm run i18n:new -w @sitekeep/web -- es Español ES es-ES
   ```
   This creates `locales/es/`: `meta.json` (`"status": "beta"`) and copies of the English files
   **with the same keys and empty values**.
2. Translate the empty values (keys stay the same; `labels.json` included). A value left empty
   shows in English, so a language can also be released half-finished.
3. Progress: `npm run i18n:status -w @sitekeep/web` (translated / total per language and namespace).
4. `npm test -w @sitekeep/web`: the key and `{{placeholder}}` checks must pass.
5. Once everything is translated, `status: "complete"`. In a `beta` language a missing key falls back to English
   and the menu shows "beta"; in a `complete` language a missing key is a test failure.

The language menu finds the folders itself (`languages.ts`, `import.meta.glob`); Vite puts each
language's files in a separate chunk, so only the selected language is downloaded. A right-to-left language
(`dir: "rtl"`) flips `<html dir>`; places in the CSS that use `inline-start/end` instead of `left/right`
are ready, the rest will be reviewed when such a language arrives.

Translation workflow: the English JSON files are the source text. The translator (human or AI)
only sees JSON; they do not need to look at the code.

## 2. File layout

```
apps/web/src/i18n/
├─ index.ts            initI18n, setLanguage, currentLanguage, currentIntlLocale
├─ instance.ts         the single i18next instance
├─ languages.ts        language list (locales/*/meta.json), default, fallback language
├─ resources.ts        English bundle (ships with the app) and namespace list
├─ labels.ts           shared enum labels: useLabel(), label(), labelEntries()
├─ i18next.d.ts        types for t() keys (from the English files)
└─ locales/
   ├─ en/  meta.json + <namespace>.json      source language
   └─ tr/  meta.json + <namespace>.json      (except labels: §5)
```

**Namespace = one part of the application:**

| Namespace | Code |
|---|---|
| `common` | buttons and states used everywhere (Save, Cancel, Delete, Loading…) |
| `shell` | `src/app/` (top bar, menu, page skeleton, language menu), `src/shared/` |
| `labels` | shared enum labels (§5) |
| `auth`, `projects`, `documents`, `works`, `reviews`, `forms`, `schedule`, `sim`, `coordination`, `reports`, `ai`, `admin`, `integrations`, `projectSettings`, `onboarding`, `viewers` | the `src/features/*` folder of the same name (`documents` also `src/pdf/`, `viewers` `src/viewers/`) |

New section: `locales/en/<name>.json` + `locales/tr/<name>.json` + one line in `resources.ts`.

## 3. Code rules

```tsx
import { useTranslation } from "react-i18next";

export function CapacityCard() {
  // First namespace = plain keys; other listed namespaces with a prefix ("common:…").
  const { t } = useTranslation(["admin", "common"]);
  return (
    <>
      <h2>{t("capacity.title")}</h2>
      <button>{t("capacity.actions.runTest")}</button>
      <p>{t("capacity.summary", { registered: 164, active: 97 })}</p>
      <button>{t("common:actions.cancel")}</button>
    </>
  );
}
```

- **No text is written in code.** JSX text, `title`, `aria-label`, `placeholder`, `alt`,
  error/notification sentences, option lists: all go through `t()`. A test checks this (§6).
- **Key = meaning, not text:** `capacity.actions.runTest`, not `"Canlı Test Et"` (Run Live Test).
  camelCase, in screen → section → name order.
- **Whole sentences, with placeholders.** No concatenation of fragments (`t("a") + count + t("b")` is wrong;
  languages change word order):
  ```json
  "summary": "{{registered}} registered, {{active}} active users"
  ```
- **Plurals:** `_one` / `_other` with `count` (i18next, `Intl.PluralRules`):
  ```json
  "files_one": "{{count}} file", "files_other": "{{count}} files"
  ```
  In Turkish both may be the same ("{{count}} dosya"); both are still written.
- **Formatted text** (bold, links): `<Trans i18nKey="…" components={{ b: <b />, a: <Link to="…" /> }} />`,
  in JSON `"<b>{{name}}</b> sizi davet etti"` ("<b>{{name}}</b> invited you").
- **Constants outside components** (menu, tab, option arrays): hold the **key**, not the text
  (`labelKey: "nav.items.today"`), translated on screen with `t(item.labelKey)`.
  `t()` is not called at module level, so that the UI re-renders when the language changes.
- **Functions outside components** (helpers, `confirm()` text): `i18n.t("ns:key")`
  (`import { i18n } from "src/i18n"`), in the language current at the time of the call.
- **Dates, numbers, sizes:** `formatDate`, `formatDay`, `formatNumber`, `formatPercent`,
  `formatSize`, `formatRelative` (`shared/lib/format`). For your own `Intl` call use
  `intlLocale()`. Never hard-code `"tr-TR"` / `"en-GB"`.
- **Data ≠ interface:** upper/lower case, search and sorting of user-entered codes, names, layer and folder names
  follow `dataLocale()` (Turkish rules: "i" → "İ"), not the interface language;
  a code typed in the English interface is the same code.
- **Not translated:** user data (project, file, folder names, notes typed in), AI
  answers, product and standard names (IFC, BCF, ISO 19650, PDF, Revit…), error texts coming from the
  server (the server answers according to `Accept-Language`; next step, §8).
- **A key from another namespace:** declare both with `useTranslation(["admin", "common"])`,
  then `t("common:actions.save")`. If only one namespace is declared, a prefixed key is a type error.

### 3.1 Key groups and capitalisation

In the interface, **names and labels** are written in Title Case ([TERMINOLOGY.md](../product/TERMINOLOGY.md)
"Capitalisation rule"), while sentences stay as sentences. Which is which follows from the key's
group and is tested for Turkish:

| Group (a segment in the key path) | What | Capitalisation |
|---|---|---|
| `title`, `heading` (last segment) | page, section, dialog title | Title Case |
| `actions.*` | button, menu command | Title Case |
| `tabs.*`, `nav.*`, `menu.*` | tab, menu item | Title Case |
| `columns.*` | table column header | Title Case |
| `options.*`, `status.*`, `badges.*` | checkbox, option, status, badge | Title Case |
| `fields.*` | form field label | Title Case (explanation in parentheses as a sentence) |
| `hint`, `help`, `description`, `empty`, `placeholder`, `confirm`, `errors.*`, `messages.*` | explanation, empty list, confirmation question, error, notification | sentence |

English follows the same distinction: labels in Title Case ("Run Test", "Upload Document"),
sentences in sentence case.

## 5. Shared labels

The Turkish names of enums such as status, priority, permission level and work category are in the
`*_LABELS_TR` tables in `@sitekeep/shared` (the server also uses them in reports and e-mails).
The web app does not read them directly:

```tsx
const label = useLabel();
label("issueStatus", issue.status);          // "Open" / "Açık"
labelEntries("folderState");                 // [["wip", "Work in Progress"], …] (select boxes)
```

- `ISSUE_STATUS_LABELS_TR` → table name `issueStatus` (suffix dropped, camelCase).
- The Turkish `labels` namespace is built from these tables at runtime (`labels.ts`); there is no `tr/labels.json`.
- Other languages translate `locales/<code>/labels.json`; the keys match the tables (tested).
- When a new `*_LABELS_TR` table is added, its English goes into `en/labels.json`; a test reminds you.

## 6. Checks (`npm test -w @sitekeep/web`)

| Test | What |
|---|---|
| `test/i18n/parity.test.ts` | every `complete` language has the same keys as English; no extra keys in a `beta` language; `{{placeholders}}` and `<tags>` match; no empty values; `labels` tables match |
| `test/i18n/hardcoded.test.ts` | no JSX text, no text-bearing attributes (`title`, `aria-label`, `placeholder`, `alt`, `label`) and no strings with Turkish letters in `src/` (excluding locales). A line that genuinely needs one carries `// i18n-ok` |
| `test/app/ui-terms.test.ts` | no English loanwords in Turkish values (Review, Issue…); Turkish values in the §3.1 groups are Title Case |

Unit tests run in Turkish (`test/setup.ts`): the existing expectations are written with Turkish text.
e2e tests also set Turkish in the browser (`e2e/support/global-setup.ts`);
`e2e/specs/language.spec.ts` tests the English default and switching languages.

## 7. Server and profile

- `PATCH /me/prefs { language }`: stores it in the profile (BCP 47 pattern). `GET /auth/me` → `language`.
- On sign-in the language in the profile takes effect; if the profile has none, the one selected in the browser is written.
- Every API request sends `Accept-Language: <language>` (`shared/api/client.ts`).

## 8. Server texts

Texts produced by the server and seen by the user are also in translation files:
`apps/server/src/i18n/locales/<language>/<namespace>.json`. Namespace = source folder
(`src/works` → `works`, `src/param-change` → `paramChange`), general ones in `errors`.
The languages are the same as the web app's (a test requires the same folders); `npm run i18n:new` creates both together.

### 8.1 Code does not write sentences, it gives names

```ts
import { msg } from "../i18n/index.js";

throw badRequest(msg("works:errors.closed", { number: work.number }));
throw notFound(msg("works:entities.work"));          // "Work not found." / "İş bulunamadı."
throw forbidden();                                   // errors:forbidden
```

`msg()` produces a **Msg**: `{ key, params }`, plain JSON. A Msg is turned into text as late as possible,
in the reader's language:

| Where | Whose language | How |
|---|---|---|
| HTTP error | the requester's | the error handler translates `HttpError.msg` |
| Notification | the reader's | `notify({ title: msg(…) })`; stored in the `notifications.message` column, translated when the list is read |
| Export (Excel, PDF, CSV), report | the downloader's | `const t = tReq(req); t("reports:columns.status")` |
| E-mail, a file produced for someone else | the recipient's profile | `tFor(profileLanguage(user.prefs))` |

Request language: `Accept-Language` (the web app sends the current interface language) → profile
(`prefs.language`) → the installation default (`CDE_DEFAULT_LANGUAGE`, otherwise English).

### 8.2 Not translated

- **Data:** default names written into the project (built-in work types, roles, folder templates,
  form library), demo data (`src/dev`), user data. So that existing projects do not break,
  data stays in the language it was first written in.
- **Text sent to the model:** AI prompts, MCP tool output, terminology instructions.
- **Log lines** (`req.log`, `console`), regular expressions that match Turkish input.

If these contain Turkish letters, they are marked with `// i18n-ok: <reason>` at the end of the line or
`// i18n-ok-file: <reason>` at the top of the file.

### 8.3 Checks

`apps/server/scripts/check-i18n.mjs`: no strings with Turkish letters left in `src/` (excluding locales, dev, scripts, db).
`test/i18n/i18n.test.ts`: languages the same as the web app, key and
`{{placeholder}}` matching, `Accept-Language` selection, errors and notifications translated for the
reader. Server tests run in Turkish (`vitest.config.ts`: `CDE_DEFAULT_LANGUAGE=tr`).

## 9. Module texts

Each SiteKeep module carries its own screen and server texts in its own repository:

```
sitekeep-<id>/locales/
├─ server/<language>/<namespace>.json   server texts (msg("contracts:…"))
└─ web/<language>/<namespace>.json      interface texts (t("contracts:…"))
```

- **A namespace can be the same as the core's.** The files are **added** to the core's namespaces (i18next
  `addResourceBundle`, deep merge). Cost brings its own `contracts` namespace, while AI adds the keys of
  the "AI and MCP" tab to the `admin` namespace. The keys stay the same in the module
  code.
- **Server:** `ServerModule.locales` (folder path, like `migrations`). The core reads it at startup with
  `registerLocaleFolder()`. A language not in the core is ignored; an empty value falls back to English.
- **Web:** the `sitekeep-modules.ts` plugin finds the `locales/web` folder of installed packages.
  English ships with the app; other languages are loaded as a separate chunk when selected
  (`addModuleLocales`, `src/i18n/index.ts`).
- **Types:** the module adds its own English files to the `SiteKeep.ServerResources` /
  `SiteKeep.WebResources` interface (`server/i18n.d.ts`, `web/i18n.d.ts`). A wrong key is a compile
  error in the module too.
- **Enum labels** (status, type …): the module's own tables. The Turkish versions are the module's `*_LABELS_TR`
  constants, registered with `registerTurkishLabels(...)` when the module loads (in the server and web
  entry points). Other languages are in `locales/shared/<language>/labels.json`; the core reads them on both
  sides. On the web, `useLabel("contractStatus", …)` is type-checked (`SiteKeep.LabelTables`).
- **New language:** a folder is created in the core (§1). The same language folder is also added to each module repository;
  if it is not, the module screens show in English.
- **Checks:** `test/locales.test.ts` in the module repository (English keys and
  `{{placeholders}}` in every language). In the core, `apps/server/test/i18n/module-locales.test.ts` and
  `apps/web/test/i18n/module-locales.test.ts` (texts of installed modules appear in both languages).
- **Which key belongs where:** if a key appears only in one module's code, it lives in that module. Keys used by the core
  or by several modules stay in the core (e.g. the shared `sim` / `schedule` keys of Planning and
  Cost).
