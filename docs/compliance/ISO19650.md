# ISO 19650 conformance

How SiteKeep Community meets the requirements that ISO 19650-1:2018 and ISO 19650-2:2018 place on a
common data environment (CDE) solution and its workflow, how to switch them on for a project, and the
automated tests that prove each one. Data model and settings: [CDE states](../features/CDE_STATES.md).

ISO 19650 is a process standard. What it asks of the software is the CDE: ISO 19650-1 §12 (CDE solution
and workflow) and ISO 19650-2 §5.1.7 (establish the project's CDE), plus the steps that share, review,
authorise, accept and archive information (ISO 19650-2 §5.6, §5.7). These are features of SiteKeep and are
mapped below. The other requirements (information requirements, the BIM execution plan, delivery plans,
the information protocol) are met by **documents** that the project keeps in the CDE; SiteKeep supplies
folders and templates for them, not features ([below](#covered-by-documents-and-templates)).

Status: **done** (shipped and tested), **partial** (part of the requirement is a feature, the rest is
configuration or a document), **planned**.

Test references read `file` › "describe" or `file` › "describe" › "test". Every one of them is in the
conformance pack (`npm run test:iso`, `npm run e2e:iso`) and is checked by `npm run iso:check`
([verification](#verification)).

## How to enable ISO enforcement on a project

**New project.** Projects → **New Project** → template **ISO 19650 Temel** (ISO 19650 Basic), or one of the
construction templates **ISO 19650 Construction Project** (English or Turkish names, [project
templates](../features/PROJECT_TEMPLATES.md)), which add the general folders for information
requirements, BEP and standards, eight workflows and the module settings. Map a company to each party
(İdare: client, Müşavir: consultant, Tasarımcı: designer, Yüklenici: contractor). The project starts with:

- the four state folders, one WIP folder per party owned by that party's task team, and the archive folder;
- the naming standard "ISO 19650 Kodlama" on Shared and Published, and the folder review gate on both;
- the code scheme `iso_uk_na`, WIP policy **Owning Task Team Only**, project administrators seeing all WIP;
- the transition table: upload → WIP; WIP → Shared through "Ekip İçi Kontrol"; Shared → Published through
  "Tasarımcı → Müşavir → İdare"; Shared → WIP and Published → Archived automatic;
- **Enforce the Transition Table** on;
- **Document Code Standard** "ISO 19650 Kodlama" (construction templates: "ISO 19650 Document Naming" /
  "ISO 19650 Doküman Kodlama"), so document codes are unique from WIP on.

**Existing project** (enforcement is off by default, so nothing changes until an administrator acts):

1. Give the top folders their states (WIP, Shared, Published, Archived) in the folder settings.
2. Project Settings → CDE → Revision and Suitability Codes: choose the code scheme. Check the values the
   migration could not convert.
3. Project Settings → CDE → Task Teams: **Create Teams for Companies**, set an owner team on each WIP
   folder, then **Who Sees WIP: Owning Task Team Only**.
4. Assign a naming standard to the Shared and Published folders, and choose the **Document Code Standard**.
   Resolve the entries in **Code Conflicts**.
5. Project Settings → CDE → State Transitions: **Use ISO 19650 Defaults**, pick the review workflow of
   each review transition and the **Archive Folder**, switch **Enforce the Transition Table** on and save.

The same settings are available over the API (`PUT /api/v1/projects/:pid/cde/settings`) and are carried
by a project template's `"cde"` block ([CDE states](../features/CDE_STATES.md#project-templates)).

## Verification

Node 22, from the repository root:

```bash
npm run iso:check   # every test this document names exists and is tagged; every tagged file is named here
npm run test:iso    # iso:check, then every ISO19650-tagged unit and API test (shared, server, web)
npm run build && npm run e2e:iso   # the ISO19650-tagged browser journeys (Chromium)
```

A test belongs to the pack when its name (describe › test) carries the tag `ISO19650`, followed by the
part and the clause: `ISO19650-2 5.1.7(a) unique container id`, `ISO19650-1 12.1 CDE labels`. The pack
runs in Community (no Enterprise modules) and in Enterprise installations alike; the same tests also run
in the full suites (`npm test`, `npm run e2e`, [tests](../architecture/tests.md)).

**The audit chain check** (`GET /api/v1/admin/audit/verify`, Project Settings → Audit Log → **Check the
Chain**, or `npm run audit:verify -w @sitekeep/server` against a database) recomputes the hash of every
audit row since the chain started and compares each row with the one before it. A result of `ok: true`
proves that no row has been changed, removed or inserted out of order since it was written, by anyone
going round the database triggers that make the log append-only. On `ok: false` it names the first
broken row and why (`hash_mismatch`, `prev_mismatch`, `missing_hash`). It does not prove that an action
was logged in the first place (the tests above show which actions are), and someone with database owner
rights could rewrite the whole tail of the chain consistently; record the head hash that the check shows
outside the server from time to time to rule that out ([audit log](../features/AUDIT_LOG.md#checking-the-chain)).
